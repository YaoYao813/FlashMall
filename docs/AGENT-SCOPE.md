## 二、这个项目是什么

**FlashMall：高并发秒杀商城配套 AI 运营决策 Agent**（2026-11-06 定名）：给秒杀商城的运营人员用的对话式控制台。
运营说一句「下周三上午十点，商品 7 上 50 件，299.9」，Agent 完成建活动、预热、巡检、数据查询，写操作必须人工确认。

解决的四个痛点，全部来自现有代码的真实缺口：

1. **没有活动管理能力**——要办一场秒杀得手工改 `seckill_event` + `product_stock` + 手动 SET Redis，漏掉预热用户直接看到「库存不足」。
2. **没有运营数据**——GMV、支付率、库存消耗率只能连 MySQL 手写 SQL。
3. **库存不一致无人发现**——回滚不幂等，Redis 与 DB 会漂移，没有任何对账手段。
4. **操作无审计**——谁改了库存、改了多少、批没批，没有记录。

一句话：**把秒杀运营从「手工改库 + 祈祷」变成「说一句话 + 人工确认 + 全程留痕」。**

## 三、V1 功能裁决（2026-11-04 定稿）

| 能力 | 结论 | 理由 |
|---|---|---|
| Subagent / 多 Agent | **不做** | 判据 ③ 未中：单 Agent 未跑通，回答不了「为什么要拆」。LangGraph 子图亦不做 |
| 记忆体系 | **只做短期**（checkpointer + Redis） | 写操作要 `interrupt()` 等确认，进程重启后审批状态不能丢——这是真实需求，不是为了有记忆而记忆 |
| 长期记忆 / 用户画像 | **不做** | 判据 ②③ 未中：任务是任务型会话，跨会话记忆没有真实场景 |
| 意图识别 | **做** | 图的首个节点，**一次结构化输出同时给出 intent + slots**，不做「先分类再抽取」两次调用 |
| RAG 知识库 | **不做** | 本项目数据是结构化的（活动、库存、订单），工具查比向量检索准。判据 ③ 答不上「为什么需要向量检索」 |
| 上下文压缩 | **只做工具返回裁剪** | 统计结果可能很长，节点内截断 / 只留 top-k。**不做**长会话摘要压缩——运营会话通常 5–10 轮结束 |
| 护栏 | **做，且是核心** | 工具白名单、写操作 `interrupt()` 确认、Pydantic 参数校验、`user_id` 只从会话取、外部文本（商品名）当数据不当指令 |
| Milvus / PostgreSQL 等大数据组件 | **不做** | 本项目 8 个活动、几张表，MySQL 足够。判据 ② 未中，且换成关键词堆砌 |
| 用户界面 | **做，单页对话台** | HITL 确认卡片没有界面就无法演示，界面是功能载体；但**不做管理后台 CRUD 页面**，管理能力全走对话 |
| 公网部署 | **不做** | 无管理员鉴权 + 有 LLM key，公开等于送额度。本地 `docker-compose` 一键起 |

## 四、V1 交付物（截止 2026-11-13 23:59）

**Java 侧 5 个接口**（seckill-service，走网关，不改已有表结构）

| # | 接口 | 说明 |
|---|---|---|
| 1 | `POST /api/admin/seckill/events` | 建活动，读 `Idempotency-Key`；同一商品不许有两场未结束活动 |
| 2 | `GET /api/admin/seckill/events` | 分页 + 状态/商品筛选；状态由时间**推导** |
| 3 | `PUT /api/admin/seckill/events/{id}` | 改时间/价格/库存（仅「未开始」）；下线 = `endTime` 提到当前 |
| 4 | `POST /api/admin/seckill/events/{id}/stock-sync` | `mode=reset` 预热 SET；`mode=increment` 运行中增量调整（DB 与 Redis 同增） |
| 5 | `GET /api/admin/seckill/events/{id}/stats` | GMV / 订单数 / 支付率 / 消耗率 + 当前 DB 与 Redis 库存 |

**秒杀链路唯一改动**：`SeckillServiceImpl.seckill()` 开头加活动窗口与库存预热校验（读 `seckill:event:{productId}`，一次 GET）。Lua 预减、MQ、乐观锁一律不动。

**Python 侧 5 个工具**（3 读 2 写）

`query_seckill_events`、`get_seckill_stats`、`diagnose_stock` / `create_seckill_event`、`adjust_seckill_stock`

**其他**：单页对话台（SSE + 确认卡片 + 工具轨迹）、25 条评测集、一页 README。

## 六、明确不做（及一句话答法）

| 不做 | 答法 |
|---|---|
| 多 Agent / Subagent | 单 Agent 已覆盖场景；没有真实分工需求时多 Agent 是纯负担，拆开只会增加调试面 |
| RAG | 这里的数据是结构化的，工具查询准确率和可解释性都更高；RAG 适合非结构化知识，用错场景比不用更糟 |
| 长期记忆 | 秒杀运营是任务型会话，跨会话记忆没有真实需求，做出来是假的 |
| Milvus / 向量库 | 没有向量检索需求，选型要看数据形态不是看关键词 |
| 从零写管理后台 | 管理能力全部通过对话完成，多写 CRUD 页面不增加面试价值 |
| Prometheus / Loki | 诊断用现有 Redis / MQ / DB 指标足够，先补可观测会挤掉主线 |
| Agent 进秒杀主链路 | 延迟不可控，旁路才安全 |
